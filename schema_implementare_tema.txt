  Structura unui segment
Există două tipuri de segmente:

Date (client → server):
| Protocol ID (1B) | Conn ID (1B) | Type (1B) | SEQ_NUM (2B) | Payload Size (2B) | Payload |

Control/ACK (server → client):
| Protocol ID (1B) | Conn ID (1B) | Type (1B) | ACK_NUM (2B) | RECV_WINDOW (2B) |

Protocol ID e mereu 42. Typul poate fi ceva gen: DATA=1, SYN=2, SYN_ACK=3, ACK=4, FIN=5


Cele 3 mari mecanisme
1. 🤝 Three-Way Handshake (stabilirea conexiunii)
CLIENT                          SERVER (port 8032)
  |                                |
  |---------- SYN ---------------->|   "vreau să mă conectez"
  |                                |
  |<--------- SYN-ACK + PORT ------|   "ok, vorbim pe portul X"
  |                                |    (portul X e ales random)
  |---------- ACK ---------------->|   "am înțeles"
  |                                |
  [ de acum înainte, pe portul X ]
  
  Clientul are un singur socket pentru tot (handshake + date)
Serverul are un socket dedicat pe 8032 pentru handshake, + câte un socket per client
1. Structurile de date și fereastra

    Insight: Asigură-te că folosești macro-ul __attribute__((packed)) exact cum e în schelet, altfel compilatorul va adăuga padding (octeți extra) și se va strica alinierea când trimiți pachetul pe rețea.

    Pentru fereastră: În interiorul struct connection, cel mai ușor este să folosești un std::vector sau un std::deque pentru buffer-ul ferestrei (atât la sender, cât și la receiver), alături de un std::map pentru a ține evidența segmentelor primite out-of-order la receiver.

2. Three-way handshake

    Atenție la server: Când serverul primește SYN pe portul principal (8032), el trebuie să creeze o nouă instanță de struct connection, un nou socket pe un port random, să le lege, și de-abia apoi să trimită SYN-ACK.

    Port random: Pentru a alege un port liber, poți face bind cu portul setat la 0. Sistemul de operare îți va aloca automat un port disponibil, pe care îl poți afla ulterior folosind getsockname.

3 & 4. Send/Recv și Selective Repeat ARQ

    Timer-ul: Cerința menționează că timer-ul este per conexiune, nu per segment. Asta înseamnă că atunci când funcția recv_message_or_timeout îți întoarce timeout, tu trebuie să retransmiți primul pachet neconfirmat din fereastra ta (acel base_seq), pentru că cel mai probabil el a blocat avansarea ACK-ului.

    ACK Cumulativ: Aici este capcana clasică. Dacă serverul are pachetele 0, 1, 3, 4, el trimite mereu ACK 2 (așteaptă 2). Când sosește în sfârșit 2, serverul nu trimite ACK 3, ci trimite ACK 5 (pentru că 3 și 4 erau deja în buffer). Logică trebuie să fie "glisantă".

5. Flow control

    Calculul: RECV_WINDOW se calculează foarte simplu la server: Capacitate_Totală_Buffer - Octeți_Stocați_Necitiți_De_Aplicație.

    Zero Window: Dacă clientul primește WINDOW=0, trebuie să nu mai trimită date noi, dar atenție: trebuie să continue să asculte, ca să poată prinde viitorul pachet de control în care fereastra se va mări din nou.

6. FIN

    Cea mai curată metodă de a închide. Te asigură că transferul s-a terminat complet, că ultimele ACK-uri nu s-au pierdut și că poți da close(sockfd) în siguranță.
2. 📦 Selective Repeat ARQ (transmiterea datelor)
Fără fereastră glisantă, trebuia să trimiți un segment, să aștepți ACK, apoi să trimiți următorul. Lent.
Cu Selective Repeat:
Fereastra senderului (ex: mărime 4):
[SEG 0][SEG 1][SEG 2][SEG 3] ---> trimise toate odată
                               
ACK 0 vine ✓  → fereastra avansează
ACK 1 vine ✓  → fereastra avansează
ACK 2 se pierde ✗
ACK 3 vine ✓  → stocat, dar fereastra NU avansează (că lipsește 2)

... timer expiră → retransmit DOAR segmentul 2
ACK 2 vine ✓  → fereastra avansează peste 2, 3

3. 🪟 Flow Control (dimensiunea ferestrei)
Serverul are un buffer intern limitat. Când se umple, îi spune clientului să se oprească:
Server buffer: [████████░░]  → trimite ACK cu RECV_WINDOW = 2  (mai am loc pentru 2)
Server buffer: [██████████]  → trimite ACK cu RECV_WINDOW = 0  (STOP!)
Server buffer: [░░░░░░░░░░]  → trimite ACK cu RECV_WINDOW = 10 (continuă!)

4. 📐 Fereastra optimă (BDP)
Mărimea ferestrei senderului se calculează din:
BDP = bandwidth × RTT
    = speed (bytes/s) × (2 × delay)

ex: 8 Mb/s = 1.000.000 bytes/s, delay = 1ms → RTT = 2ms
BDP = 1.000.000 × 0.002 = 2000 bytes → ~fereastra optimă
Asta se configurează în init_sender(speed, delay).

Arhitectura cu thread-uri
Aplicație (main thread)              Protocol thread (background)
        |                                      |
  send_data(buff) ──→ [buffer intern] ──→ send_handler: trimite segmente
                                               ↑↓
  recv_data(buff) ←── [buffer intern] ←── recv_handler: primește ACK-uri/date
  
 Mutex-ul con_lock sincronizează accesul la buffer între cele două thread-uri.
 
 
 Schema completă a unui transfer
 CLIENT                                          SERVER
  |                                               |
  |──── SYN ─────────────────────────────────────>|
  |<─── SYN-ACK + port X ─────────────────────────|
  |──── ACK ─────────────────────────────────────>|
  |                                               |
  |──── DATA [0] ────────────────────────────────>|
  |──── DATA [1] ────────────────────────────────>|
  |──── DATA [2] ─────────── (pierdut) ──────── X |
  |──── DATA [3] ────────────────────────────────>|
  |                                               |
  |<─── ACK(1), WINDOW=5 ─────────────────────────|  (cumulativ, 0 și 1)
  |<─── ACK(1), WINDOW=5 ─────────────────────────|  (3 primit, dar așteaptă 2)
  |                                               |
  | [timer expiră]                                |
  |──── DATA [2] retransmis ─────────────────────>|
  |<─── ACK(3), WINDOW=4 ─────────────────────────|  (acum are 2,3 → ACK cumulativ)
  |                                               |
  | ... continuă ...                              |
  |──── FIN ─────────────────────────────────────>|
  
  
  Ce implementăm concret (în ordine logică)

1. Structurile de date — headerele, struct connection, fereastra
2. Three-way handshake — setup_connection() și wait4connect()
3. Send side — send_handler: trimite din fereastră, gestionează timeout, retransmite
4. Recv side — recv_handler: bufferează segmente out-of-order, trimite ACK-uri cumulative
5. Flow control — fereastra receiverului în ACK, senderul se oprește la WINDOW=0
6. FIN — închiderea conexiunii
